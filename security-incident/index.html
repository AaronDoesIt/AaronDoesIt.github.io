Home PC Security Incident — Technical Breakdown

  • System: Home Windows desktop workstation
  • Discovered and remediated: July 2026
  • Classification: Confirmed compromise. Unauthorized remote access used for an infostealer / stolen-session fraud operation.

Names, network addresses, port numbers and other details that could identify the owner or the machine have been removed. The rogue account names are kept on purpose: they are the attacker's, and they are useful to anyone checking their own machine.

1. Summary

A home Windows workstation was found to have been taken over and used as a worker machine in a fraud operation built on stolen browser cookies. Five local administrator accounts the owner never created had been added to the machine. Over a long period, the attackers used them to log in over Remote Desktop (RDP), load collections of stolen browser cookies belonging to other victims, and run a credential-stealing tool against the browser profiles on the machine, including the owner's own Chrome, Firefox and Opera data.

All five accounts and their profiles were deleted, and remote access was rebuilt so the machine can only be reached over a private, authenticated Tailscale network instead of the open internet.

2. The unauthorized accounts

Each of the five accounts was enabled and a member of the local Administrators group. Three were also in Remote Desktop Users, which allowed them to log in remotely. The names are random eight-character strings, which is typical of accounts created by a script rather than a person.

3. Why these accounts were clearly hostile

  • Naming: random eight-character names, the pattern of script-generated backdoor accounts.
  • Privileges: every account was enabled with full administrator rights, and three could log in over RDP.
  • Created one after another over time: the account IDs and password-set dates show the accounts were added in sequence over roughly 19 months. This was repeated, deliberate access, not a single event.
  • Language clue: pizdatZz is Russian slang, not a Windows default and not anything the owner would have created.
  • Recent use: logon timestamps showed activity into early 2026. The accounts were in active use, not leftovers.

4. What the attackers were doing

The evidence points to the machine being used as a working node for account takeover with stolen session cookies:

  • Hands-on remote control: the rogue accounts logged in interactively over RDP to operate the machine.
  • Stolen victim data brought in: collections of stolen browser session cookies belonging to third-party victims were loaded onto the machine. This fits using it to test or cash in stolen logins from a clean-looking home connection.
  • Credential theft from the machine itself: a tool aimed at Windows DPAPI-protected browser data was run. Execution of dpapimig.exe was confirmed. Tools of this kind pull saved passwords, cookies and tokens out of browser profiles; here they targeted the owner's Chrome, Firefox and Opera profiles.

Note for readers checking their own systems: dpapimig.exe is also the name of a genuine Windows utility in System32 that migrates DPAPI keys. Seeing that file name on its own is not proof of compromise. Check its path and digital signature against the System32 original.

What this meant for the owner: every password, cookie and session token saved in the browsers on that machine had to be treated as stolen.

5. How they likely got in

Several settings on the machine left it exposed:

  • Remote Desktop was open on the network and, at the time, probably reachable from the internet through a router port-forward.
  • SSH was reachable and allowed password logins, an easy target for automated password guessing.
  • Windows file sharing (SMB) was listening on the machine.
  • The owner's own Windows account did not require a password, which removed the main barrier on local logons.

6. What couldn't be recovered

In May 2026, before the intrusion was found, the machine was restored from a full disk-image backup. That restore overwrote the older Remote Desktop connection logs. As a result, the attackers' source IP addresses for earlier sessions are gone, and the exact way in and the full timeline can't be rebuilt from the machine's own logs. Activity tied to the accounts spans roughly September 2023 through early 2025, with logons continuing into 2026.

7. Cleanup performed

  • Rogue accounts removed: all five accounts and their user profiles were deleted. Only the owner's account and the disabled built-in accounts remain in the Administrators and Remote Desktop Users groups.
  • Remote Desktop taken off the public internet: Tailscale was installed, and the Windows firewall now accepts RDP only from Tailscale's private address range (100.64.0.0/10). Reaching the machine now requires an authenticated Tailscale connection.
  • Internet-facing firewall rules shut off: 38 firewall rules that had exposed the RDP port to the internet were disabled, to be deleted once RDP over Tailscale was confirmed working.
  • Account protections turned on: account lockout after 5 failed attempts in 15 minutes, and a 12-character minimum password length.

8. Follow-up actions

  • Check for a second way in: the Chrome Remote Desktop host service (remoting_host.exe) was found running. It had to be confirmed as the owner's own tool or removed as possible attacker persistence.
  • Change every saved password: from a known-clean device, change every password that had been saved in the browsers, and turn on two-factor authentication wherever it's offered.
  • Lock down SSH: limit it to the Tailscale network and switch from passwords to key-based login.
  • Put a password on the owner's account: make sure a password is required and set a new one.
  • Remove the disabled firewall rules once the Tailscale-only path is confirmed.

9. Outcome

The active intrusion was shut down: all five rogue administrator accounts were deleted, and the remote access that made the compromise possible was cut back to a single authenticated private-network path. Anything saved in the machine's browsers had to be treated as exposed until it was changed.

Checking your own Windows PC

The same signs are easy to look for. In an administrator PowerShell window:

  • Get-LocalUser lists every local account. Look for names you don't recognize, especially random-looking ones.
  • Get-LocalGroupMember Administrators and Get-LocalGroupMember "Remote Desktop Users" show who has admin rights and who can log in remotely.
  • Get-LocalUser | Select Name,SID,Enabled,PasswordLastSet,LastLogon shows account IDs (the last number in the SID). Gaps in the sequence mean accounts were created and deleted.
  • Check your router for port-forwards to 3389 (RDP), 22 (SSH) or 445 (SMB), and make sure your Windows account has a password.
